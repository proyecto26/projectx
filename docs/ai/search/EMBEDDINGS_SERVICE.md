## Packages and apps

1. `packages/embeddings` (private, `@projectx/embeddings`), no NestJS dependency, unit-tested in `verify`:

   - `TransformersEmbedder` (`@huggingface/transformers` pinned exactly, model `onnx-community/embeddinggemma-2-ONNX` at revision `daa72c51…`, dtype `q4`, weights read from the verified revision directory `MODEL_CACHE_DIR/<model>/<revision>/` as a plain local path, with `env.allowRemoteModels = false` and `env.useFSCache = false`; the library's revision-keyed cache is not used because its tokenizer lookup ignores the revision (found while implementing: offline it fails, online it silently reads `main`; the spike's tokenizer therefore came from `main`, so its measurements stand but parity fixtures must be computed with the pinned files). Two modes: `text` (config `vision_config = audio_config = null`, text session only, 2 threads) and `full` (vision + text, 4 threads). Query text gets the `SearchQuery` prompt (`task: search result | query: `); images get no prefix; a mixed item puts `<|image|>` in the text. `profile()` returns `{ model, modelRevision, dims: 768, dtype: "q4", runtime: "transformers.js@<exact version from its package.json>", documentTemplate: "image", queryPrompt, imageTokenBudget }`.
   - `FakeEmbedder`: deterministic (SHA-256 of the input expanded to 768 floats, normalized), same `profile()` shape with `runtime: "fake"`, so fake vectors can never mix with real ones in one profile.
   - `PriorityPermit` (one holder at a time) with lanes `query > interactive > bulk`: `acquire(lane, signal): Promise<Release>`; strict priority, but after 20 consecutive grants to higher lanes while a lower lane waits, the oldest lower-lane waiter goes next; `query` lane admits at most 4 waiters (`PermitFull` otherwise, mapped to 503); acquisition rejects on `signal` abort and removes the waiter; release is idempotent. Pure logic, exhaustively unit-tested (ordering, starvation bound, abort while waiting, abort after grant, double release, full queue).
   - `BlobReader` interface `get(storageKey, signal): Promise<Uint8Array>` with an S3 implementation (`@aws-sdk/client-s3`, env from VISUAL_SEARCH.md Storage: endpoint, region, path style, credentials; size cap 20 MB, timeout 30 s) and an in-memory one for tests. Reads never happen while holding the inference permit (see Activity contract).
   - Model provisioning: `pnpm --filter @projectx/embeddings models:fetch` downloads the pinned revision's files (q4 ONNX, tokenizer, processor, config) into `MODEL_CACHE_DIR` and checks each against `models.lock.json` (path, size, sha256), committed in the package; `models:verify` only checks. Both roles verify the lock at startup and exit 1 on a missing or mismatched file, so a process never downloads or runs other weights. Compose runs `models:fetch` in a one-shot `model-fetch` service both roles depend on (`service_completed_successfully`); a deployment runs the same command as an init job against its volume.
2. `apps/embeddings` (NestJS 12, root Dockerfile), one image, role chosen by `EMBED_ROLE`:
   - `text`: `POST /embed/text` `{ texts: string[] (1–8, each ≤ 2 KB) }` → `{ vectors: number[][], profile, ms }`; p-limit 1; at most 16 requests waiting (503 beyond), a 5 s deadline (504; the queue wait is abandoned, an inference already running finishes and its late result is discarded), and a client that disconnects leaves the queue (detected on the response `close`, not the request's, which fires once the body is read); `GET /health` 200 only after the model loaded and a warm-up inference ran.
   - `image`: `POST /embed/image` (multipart image ≤ 10 MB, optional `text`) → `{ vector, profile, ms }`, query lane, 20 s deadline (the deadline aborts permit acquisition; an inference already running finishes and is discarded); two activity-only `@temporalio/worker` `Worker`s (no workflow bundle, `workflowsPath` unset) on task queues `embeddings-interactive` (max 2 concurrent activities) and `embeddings-bulk` (max 1), sharing one `PriorityPermit`; `GET /health` reports model ready, the interactive worker `RUNNING`, and the bulk worker `RUNNING` or `PAUSED` (stopped on purpose outside `BULK_INGESTION_WINDOW`: healthy, shown in the details); a failed worker is unhealthy.
   - Internal network only: no host port in compose for `embed-image`'s HTTP besides debug; `embed-text` likewise. The search API (step 5) is the only caller.
   - On startup (both roles) `ensureProfile(embedder.profile())` and keep the id (`registeredProfileId`); a conflicting registration is fatal (exit 1). HTTP responses return that id with each vector, so the search API can refuse a vector from another profile.
   - Graceful shutdown: workers `shutdown()` and drain (in-flight item finishes, its heartbeat records the checkpoint), HTTP stops accepting, then exit.

## Activity contract

`embedAssets({ items: { assetId, generation }[] (1–500), profileId, dispatchId })` → `{ embedded: number, failed: { assetId, code, retryable }[], skipped: { assetId, reason }[] }`, where `code` and `reason` come from closed sets of at most 32 ASCII characters, so 500 items serialize to at most ~40 KB (worst case asserted in a test, under the 256 KB limit).

Profile binding: before any item, `profileId` must equal the worker's `registeredProfileId`; otherwise the activity fails with non-retryable `ApplicationFailure` type `ProfileMismatch` and touches nothing. A worker therefore only writes vectors its own embedder produced (fake and real, or two runtime versions, never share a profile id because `runtime` is part of the profile identity).

### Duplicate work (repair vs batch)

Correctness never depends on exclusive ownership. Every effect of the embedding path is fenced by `(asset_id, ingest_generation)` under the asset row lock and is idempotent, and concurrent outcomes have a fixed precedence (see Failures): `writeEmbedding` upserts the same vector for the same generation and profile, `markStored` is a no-op once stored, `markFailed` neither counts attempts nor overrides a success or a terminal failure. Two different dispatches of the same item (a batch and a repair) are two attempts; the deadline deferral makes that rare. Two workers embedding the same item (a batch and a repair, or a zombie attempt and its replacement) end in the same state as one; the only cost is the extra inference. That cost is kept small, not prevented:

- Every item is checked right before inference (step 1); an item already embedded for this generation and profile costs one indexed read, no inference.
- `next_attempt_at` (the repair deadline) is pushed ahead for queued or running work: the dispatcher (step 4 workflows) calls `beginAttempt(fences, dispatchId, deferSeconds)` before scheduling the activity (it counts one attempt per dispatch and defers the deadline, see Failures), with `deferSeconds = scheduleToStartTimeout + startToCloseTimeout`; the running activity calls `deferRepair(fences, 15 min)` on each heartbeat for its pending items (deadline only, no attempt). Both only move a deadline later, only for live, non-embedded rows of the given generation that are not terminal.
- Retries are driven by the workflow, not by Temporal's activity retry: the embedding activities run with `maximumAttempts: 1` and a `scheduleToStartTimeout` (bulk 6 h, interactive 5 min). On any failure or timeout, including `WorkerShutdown` and schedule-to-start timeouts while bulk workers are stopped outside `BULK_INGESTION_WINDOW`, the workflow calls `beginAttempt` again and reschedules (with backoff, within its own attempt budget), so no attempt is ever queued without a deferred deadline.
- If a deadline still passes (a backlog longer than the estimate), repair may embed an item a batch also embeds: correct, counted in a `duplicate_inference` metric (a write that found the same generation already embedded), and the estimate is tuned from it.

### Failures

Precedence, enforced in the repository under the asset row lock (step 2 code, unmerged), so the order in which overlapping attempts finish never changes the end state:
1. Success wins. `writeEmbedding` for the current generation and object succeeds from `stored` or `failed` (retryable or terminal: the same bytes were embedded by another attempt), sets `embedded`, clears `error`, `error_code` and the deadline. After that, `markFailed` changes nothing (`stale`).
2. A terminal failure stays terminal. Terminal means `status = 'failed' AND next_attempt_at IS NULL`. A later `markFailed` (retryable or not) leaves the row and its error unchanged; after storage (`stored_at IS NOT NULL`) `scheduleRepair` (same-content publication, resumed replacement), `markStored` (returns `terminal`), `beginAttempt` and `deferRepair` leave it unchanged too. Only success, a new generation (restore, content replacement, an admission with a different content fingerprint) or an explicit admin retry clear it. An admission with the same admission key as the current generation reuses it whatever the status, including `failed`: a terminal asset stays terminal (the admission returns `terminal`), a retryable one keeps its attempts and deadline. Today `admitAsset` gives a failed asset with the same key a new generation with `attempts = 0`; step 3.2 changes that, with tests for a failed and an exhausted duplicate admission. Before storage (`stored_at IS NULL`, e.g. an invalid download), a later successful publication of the bytes is real progress and reschedules repair, as today.
3. Attempts are counted per dispatch, not per failure or per execution. A dispatch is one scheduling of the work by a workflow (first dispatch, each workflow-driven retry, each repair run), identified by `dispatchId = <workflowId>/<runId>/<seq>`, where `seq` is a counter in workflow state (deterministic on replay). Each counted dispatch is a row in `asset_dispatch (asset_id, ingest_generation, dispatch_id)`, primary key on all three, so a dispatch is counted at most once no matter how calls interleave (a single "last dispatch" column can't do that: A commits and loses its acknowledgement, B commits, A retries and would count again). `beginAttempt(fences, dispatchId, deferSeconds)` runs as a local activity (durations, so deadlines come from the database clock) before scheduling, in one statement per batch: `INSERT INTO asset_dispatch ... ON CONFLICT DO NOTHING RETURNING asset_id` for the live, non-terminal rows of the given generations, then `attempts = attempts + 1` only for the rows that insert returned; every live, non-terminal row gets its deadline deferred. A retry after a lost acknowledgement or a replay inserts nothing and only defers: an existing dispatch stays admitted (returned as included) even when `attempts` reached the cap through it, unless the row is already terminal. The cap applies only to new dispatch ids: a new dispatch for a row at `attempts >= 5` inserts nothing, terminalizes the row (`attempts_exhausted`) and is returned as excluded. So with A as the fifth dispatch: A, lost acknowledgement, A again keeps A admitted; A, B (new), A again ends terminal after B and A is then excluded (the budget was spent; a success from an A activity already running still wins).

   One budget per generation covers every stage. The ingest workflow calls `beginAttempt` with the current fence and the run's `dispatchId` before every stage it schedules (stage, download, publish, embed): the first call counts the dispatch, the next ones only refresh the deferral with that stage's timeouts, and after a content replacement (a new generation) the same call admits the new generation, which is counted once. `publishObject` (same generation), `markStored` and `scheduleRepair` keep a later deadline (`GREATEST`) instead of resetting it to 15 minutes. Each repair run is one dispatch; `embedAssets` batches dispatch their items the same way. `markFailed` never counts, whatever the stage (`markFailed(fence, null, ...)` before publication included; the existing integration test that expects it to increment changes to expect `beginAttempt` to count). Retries that don't reach the work reuse the same `dispatchId` and so never spend budget: schedule-to-start timeouts, `WorkerShutdown`, and waits while bulk workers are paused outside `BULK_INGESTION_WINDOW`. Only a failure where the activity actually processed the item (fetch, decode, publish or inference error) makes the workflow take a new `dispatchId` for its next try. A new generation deletes the `asset_dispatch` rows and resets `attempts`. A new generation (admission, restore, content replacement) deletes the asset's `asset_dispatch` rows in the same transaction that bumps the generation and resets `attempts`, so the table holds at most cap + 1 rows per asset; asset deletion cascades. Rows already at the cap (`attempts >= 5`) are not incremented: they become terminal (`failed`, `error_code = 'attempts_exhausted'`, deadline null) in the same statement and are returned as excluded, so the dispatcher leaves them out. `markFailed` only records `error`, `error_code` and the backoff computed from the current `attempts` (terminal only when the error is not retryable; the cap is enforced in one place, at admission: after a fifth failed dispatch the row keeps a deadline and the next dispatch, usually repair, terminalizes it with `attempts_exhausted`).
4. A workflow that gives up (its own retry budget spent, or a non-retryable outcome such as `ProfileMismatch`) calls `exhaustAttempts(fences, dispatchId, code)` for the items it dispatched: rows of that generation that are still live, not embedded and not terminal, and whose latest counted dispatch (highest `asset_dispatch.seq` for the generation) is this one, become terminal with the given code; a newer overlapping dispatch, or a dispatch never counted for the current generation, terminalizes nothing (`dispatch_failed`, `profile_mismatch`); rows embedded meanwhile are untouched (success wins). Items never reached by an activity (schedule-to-start timeouts, an activity that failed before its loop) are therefore never left between states, and repair, which only picks rows with a deadline, can't exceed the cap.

Error codes (`error_code`, closed set): `fetch_timeout`, `storage_unavailable`, `object_missing`, `too_large`, `decode_failed`, `unsupported_image`, `inference_failed`, `attempts_exhausted`, `dispatch_failed`, `profile_mismatch`, `unknown`. `error` keeps the full diagnostic (up to 2,000 characters) in the database only; activity results and `batchOutcome` carry the code.

Tests (repository, against PostgreSQL): failure/failure (two attempts fail the same item: one attempt counted, one error), failure/success in both orders (end state `embedded`, error cleared), terminal then retryable failure (stays terminal, error unchanged), terminal after storage then delayed `publishObject` / `markStored` / `beginAttempt` / `deferRepair` / resumed replacement (unchanged), attempts reaching 5 only after 5 dispatches; `beginAttempt` retried with the same `dispatchId` after a lost acknowledgement counts once, also when another dispatch committed in between (A, B, A again: `attempts = 2`), and when A and B run concurrently; the sixth dispatch terminalizes with `attempts_exhausted`; at the cap, A (fifth) with a lost acknowledgement stays admitted on replay, and A, B, A ends terminal with A excluded; five dispatches that each fail before storage (`fetch_timeout`, retryable) leave the asset `failed` with a deadline and the sixth terminalizes it; a schedule-to-start retry with the same `dispatchId` doesn't count; `exhaustAttempts` terminalizes pending rows and leaves embedded ones.

### Per item

Resuming after the checkpoint in `heartbeatDetails` on retry:
1. Read the item with a new repository method `embeddingInput(fence, profileId)` (no lock): `{ storageKey, status, storedAt, retryable, embedded }` (`embedded`: the current generation has an `asset_embedding` row for `profileId`) or a fence rejection. `stale` / `deleted` → `skipped`. `embedded` true → nothing to do (see Outcomes). Status `admitted`, or `failed` with `storedAt` null (bytes never stored) → `skipped` `not_ready` (publication is the ingest workflow's job). Status `failed`, `storedAt` set and retryable: if this dispatch recorded that failure (`failedInDispatch`, a restart of the same dispatch) → nothing more (the next dispatch retries it after its backoff); otherwise `markStored(fence, storageKey)` moves it back to `stored`, then continue; terminal → `skipped` `terminal`, no inference.
2. Read the bytes (`BlobReader.get`) outside the permit, through a separate fetch limiter (2 concurrent per process, 30 s timeout, aborted by the activity's cancellation signal); the next item is prefetched while the current one is embedded, so bytes are ready when the permit is granted.
3. `permit.acquire(lane, signal)` (lane from the task queue). Liveness doesn't depend on the steps: an activity-wide timer heartbeats every 10 s from the start of the activity to its end (reads, permit waits, inference, database transactions and their retries included), independent of the database; `deferRepair` for the pending items runs on its own cadence (every 5 min, best effort, its failure only logged). The permit covers inference only: `embedder.embedImages([{ bytes }])`, then release (in `finally`). The longest a query waits for a bulk item is one inference (~3–6 s), never a download.
4. `writeEmbedding(fence, storageKey, profileId, vector)`; `ok` → embedded (also after a concurrent failure, see Failures); `content_changed` / `stale` → nothing more to do for this item.
5. On error: `markFailed(fence, storageKey, { code, message, retryable }, dispatchId)` (the dispatch row records `failed_at`) (retryable codes: `fetch_timeout`, `storage_unavailable`, `inference_failed`; terminal: `object_missing`, `too_large`, `decode_failed`, `unsupported_image`). The activity itself fails only for infrastructure errors that should retry the remaining batch (database unreachable).
6. The heartbeat details carry `{ next }` (observability only).

No checkpoint is needed for correctness: a rescheduled activity starts from the first item and skips finished ones in step 1 (one read each). Heartbeats carry `{ next }` for observability only.

Outcomes are defined by the database, read once at the end for every input fence: a new repository read `batchOutcome(fences, profileId)` returns, per item, `embedded` (the current generation has an embedding for the profile, whoever wrote it), `failed` with the asset's current `error_code` and `retryable` (status `failed`; `retryable` = deadline set), or `skipped` with a reason (`stale`: generation moved on; `deleted`; `not_ready`: no stored bytes yet; `pending`: none of the above). `failed` means the current state of the asset, not who recorded it; repair owns retries. The result is the same whether or not an attempt crashed in between. Tests: a storage read slower than `heartbeatTimeout` and a database lock wait of 25 s (under the 30 s transaction timeout; a longer wait is an infrastructure failure: the activity fails and the workflow retries with the same `dispatchId`) both complete without a heartbeat timeout; a process killed between an embedding commit and its heartbeat, and an infrastructure failure at item 250 followed by a rescheduled attempt; both results equal a run without failures.

Timeouts (set by the step 4 workflows, documented here): `heartbeatTimeout` 60 s, `startToCloseTimeout` 2 h for bulk batches, 5 min for interactive; activity `maximumAttempts: 1`, retries by the workflow (see Duplicate work), never after `ProfileMismatch`.

Cancellation and shutdown never complete a batch with pending items. Any error is first checked against the activity's cancellation signal: once it is aborted, for any reason in `Context.current().cancellationDetails` (`workerShutdown`, `cancelRequested`, `timedOut` after a heartbeat or start-to-close timeout, `notFound` when the server no longer knows the task, `paused`, `reset`), the activity stops: no `markFailed` for the item in flight (an interrupted read or permit wait is not an asset failure), no further writes, and the timer stops. It then throws `ApplicationFailure` `WorkerShutdown` on `workerShutdown`, the `CancelledFailure` otherwise. The workflow treats `WorkerShutdown`, timeouts and `paused` / `reset` as retries with the same `dispatchId` (they didn't fail the item), and cancellation as the end of the dispatch. A timed-out execution that still reaches a write before noticing is harmless: writes are fenced by generation, idempotent, and success wins. A successful result always covers every item. Test with real workers (`TestWorkflowEnvironment`): shut a worker down mid-batch, start a new one, and the batch completes with the full result; a heartbeat timeout during a slow fake read records no failure for that item.

## @nestjs/ai and the Vercel AI SDK (reviewed 2026-11-15, round 11: approve_with_changes 0.94)

Not adopted for this feature. `@nestjs/ai` (0.0.2, ESM, peers `ai@^7` and `@nestjs/resilience`; `@nestjs/workflows` optional) gives `AiService.embed` / `embedMany` over AI SDK providers, with per-request timeouts (60 s), retries (3 attempts), rate limits, usage and cost events. Its embedding contract is text only (`embedding-call.ts` rejects non-strings; `EmbeddingModelV4` takes `values: string[]`), so image and mixed inputs can't go through it, and its value (HTTP retries, token cost, parallel provider calls) doesn't apply to an in-process CPU model, while the hard parts here (lane priority, a permit per inference, memory isolation, fenced writes) aren't covered. Lessons it shares with this design: no model fallback for embeddings (the profile), index in groups and save each item (the activity), a fake model for tests (`FakeEmbedder`); bounded, cancellable admission is applied to `/embed/text` (see Packages and apps).

When the project adds language-model features (chat, agents, LLM captioning), `@nestjs/ai` is a candidate for those, decided on its own. If the text lane is ever exposed as an AI SDK `EmbeddingModelV4`, it must stay a client of the `embed-text` HTTP service (no second model copy in the caller), keep query-only semantics (the adapter always applies the search-query prompt; documents are never embedded through it), check the returned `profileId` against the expected profile, and declare `maxEmbeddingsPerCall: 8` and `supportsParallelCalls: false`.
